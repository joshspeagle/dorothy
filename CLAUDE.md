# CLAUDE.md

DOROTHY infers stellar parameters, abundances and their uncertainties from spectra (DESI, BOSS, LAMOST LRS and MRS) with neural networks trained on APOGEE and GALAH labels. All data come from one HDF5 super-catalogue with one row per star (Gaia DR3 source ID).

## Layout

- `dorothy/`: the package. `config/` holds the experiment configuration, `data/` catalogue loading and training data, `models/`, `losses/`, `training/`, `inference/` (checkpoints, prediction, evaluation), `analysis/` (saliency, anomaly detection, label-source comparison), `visualization/` and `cli/` (the `dorothy` command).
- `scripts/build_catalogue_v2.py`: builds the super-catalogue from the cross-matched FITS files in `data/raw_catalogues/`. `scripts/legacy/` holds the deprecated v1 pipeline.
- `tests/`: the test suite. `tests/synthetic.py` writes small v2 catalogues (all four surveys, both label sources) for end-to-end tests.
- `examples/`: training configurations (`variant*.yaml`) and saliency scripts.
- `docs/`: the documentation site (Sphinx with the Furo theme, Markdown pages through MyST, `docs/conf.py`), published to https://joshspeagle.com/dorothy/. `docs/figures/` holds its SVG figures, `docs/_static/` the logos and stylesheet, `docs/references.bib` the bibliography; `docs/dev/` holds development notes, which the site excludes.
- `CHANGELOG.md`: user-visible changes since the last release.
- `d5martin/`: the original notebooks (gitignored).

## Commands

- Set up: `pip install -e ".[dev]"`. Docs tools: `pip install --group docs` (pip 25.1 or later).
- Test: `python -m pytest tests/ -q`. `tests/test_masking_performance.py` asserts wall-clock times and can fail on a loaded machine.
- Lint and format check: `black --check dorothy tests scripts examples && ruff check dorothy tests scripts examples`.
- Docs: `sphinx-build -W --keep-going docs docs/_build/html`. Warnings are errors, so a malformed docstring fails the build.
- CI runs the lint check and the tests on Python 3.10 to 3.12 for every push and pull request to `main`, and builds the docs; pushes to `main` deploy them.

## Git

- After the cleanup, every change reaches `main` through a pull request, except a minor change and the revert of a commit that broke CI.
- One issue per goal. One logical change per branch, from `main`, named `<issue>-<slug>` with a lowercase hyphenated slug.
- A commit makes one small change and passes every test that passed before it. Subject in the imperative, at most 72 characters; a body only for why.
- Push a commit only after the commands under Commands pass locally.
- Never force-push `main`. Never rebase, reset or amend a pushed commit on `main` or on a branch a human has committed to.
- If CI fails on `main`, Claude reverts the breaking commit at once (`git revert -m 1` for a merge commit), runs the commands, links the failed run in the commit body and pushes the revert. If the revert conflicts or does not make CI pass, Claude opens an issue instead.
- A minor change has at most 10 changed lines, edits only prose (documentation, comments, docstrings) and changes no behaviour, public API, number, dependency, test or CI workflow. When unsure, it is not minor. Claude pushes it to `main` directly.

## Pull requests

1. Make the first commit, push it, and open a draft that closes its issue.
2. Record each decision under "Decisions". A decision is a choice that another competent developer could make differently and that affects behaviour, the public API, a number, a tolerance, a dependency or the process.
3. Run `/simplify`, then `/code-review high`; a pull request that changes only prose runs `/code-review high` alone. Fix each valid finding and answer the rest in the pull request.
4. Mark it ready when its checklist is done. Merge it with a merge commit when CI passes, no review thread is unresolved and every required approval is given.

- A behaviour change alters a result for the same inputs and seed: a prediction, a metric, the selected stars or the split, a default, or the meaning of a file in a checkpoint or catalogue. It needs a test that shows the new result and a line under "Behaviour changes" in `CHANGELOG.md`.
- Every change updates what it makes stale in `README.md`, `CLAUDE.md`, `docs/` and docstrings. Each user-visible change gets a line under "Unreleased" in `CHANGELOG.md`.
- A pull request that the lead or a collaborator reviewed or committed to merges only after that person approves it.

## Code

- Write the minimum code that is correct, clear and fast. Prefer removing to adding; deleting a concept beats adding a flag.
- Write no code when the change is not needed, or when the codebase, numpy or torch already does it.
- Validate public inputs early, with errors that name the argument and what was expected. Internal functions trust their callers.
- Public functions never modify their input arrays, unless an explicit option (such as `inplace=True`) asks for it.
- No no-ops (passing a default, guarding a case that cannot happen), dead code, or linter-ignore rules.
- One purpose per function, one group of things per module. Add a helper only when it is reused or a function is too long.
- Type hints on every public signature.

## Numerics and data

- Each of these has one implementation, which training, evaluation and prediction share: data selection and splits (`load_training_data`), spectral preprocessing (`zero_invalid_pixels`, `normalize_spectra`), label normalization (`LabelNormalizer.transform_labels`), the predicted scatter (`losses.predicted_scatter`) and its calibration (`calibrate_scatter`), and the model forward pass per label source (`forward_label_sources`). Never reimplement one of them in a caller.
- Formats: spectra `(N, 3, n_wavelengths)` = [flux, sigma, mask]; labels `(N, 3, n_parameters)` = [values, errors, mask]; model outputs `(N, 2, n_parameters)` = [mu, ln_s] in normalized units. `docs/methods/preprocessing.md` defines them.
- Masked entries can hold any value, including NaN and infinity. Select with the mask (`torch.where`, boolean indexing) before arithmetic; never multiply by the mask.
- Parameter names and their number come from the catalogue's `parameter_names` attribute. Never hard-code 11 parameters.
- Randomness comes from the configured seed: `numpy.random.RandomState(seed)` for the split, seeded generators for augmentation and initialization.
- A change for speed keeps results bit-identical, or states the measured difference and why it is acceptable.

## Tests

- Hermetic: no network, no data files outside the repository, no absolute paths. Use `tests/synthetic.py` for catalogues.
- Write a test only when it catches a plausible bug in this code that no other test catches.
- Test contracts, invariants, agreement with a reference implementation (each fast path against the direct computation), and regressions (each bug fix adds a test that fails without it). Do not test numpy's, torch's or pydantic's behaviour.
- Evaluation must reproduce the training validation metrics for every data layout (`tests/test_end_to_end.py`).
- Statistical tests are seeded, with tolerances justified by the noise.
- Name a test as a sentence that states the behaviour: `test_fully_masked_spectrum_is_rejected`.

## Documentation

- A public module has a docstring that starts with a one-line summary. A public class, function or method has a Google-style docstring: a one-line summary, the equation it implements if any, `Args:` and `Returns:` with shapes and units, `Raises:` for errors a caller can handle, and the cost when it is not obvious.
- Private code needs no docstring; give it one only when its contract is not obvious from its name and signature. A comment explains only a non-obvious why, such as a numerical subtlety.
- Docs state only what the code does now. Each fact has one home: the pages in `docs/` explain the background, the methods and how to use the code, the API reference is generated from docstrings, and `README.md` is a short introduction that links to the site. Why a change was made goes in its commit, issue or pull request.
- A docs page that explains a method shows its equations and, where a picture helps, an SVG figure in `docs/figures/` drawn with `currentColor` so it follows the light and dark themes. Cite papers with `{cite:p}` and entries in `docs/references.bib`.
- Configuration fields are documented once, in their `Field` descriptions in `dorothy/config/schema.py`.

## Measurements

- State only measured figures, or figures computed from them with the computation shown.
- A benchmark records the commit, machine, thread settings and library versions. Figures from different setups are not compared.
- A change expected to affect speed reports a benchmark against `main` (interleaved runs, medians) in its pull request.

## Agents

- Delegate implementation through self-contained briefs. Numerical or architectural work goes to the session's own model, routine work to a faster one. Each use of a more expensive model needs the lead's approval.
- Subagents never push. Claude reads every line a subagent writes before it reaches `main`.
- Parallel subagents that write files get separate worktrees.

## Writing

- Spartan: the fewest words that stay exact. Cut restatement, hedges and lists of what did not change; keep the background a new reader needs.
- Literal over metaphor. No em dashes.
- Session replies lead with the answer, then the reason, then the next step.

### Text on GitHub

Issues, pull requests, comments and commit messages have readers who are new to the code. This text follows these rules, adapted from ASD-STE100 Simplified Technical English:

- Lead with a summary, then the background a new reader needs.
- Short sentences: at most 20 words for an instruction and 25 for a description. One idea per sentence, at most six sentences per paragraph.
- Active voice, simple tenses, and full sentences with articles.
- One word for one meaning, and the same term for the same thing everywhere. Define each term and abbreviation where it first appears.
- Noun groups of at most three words.
- A condition comes before the instruction it controls. Numbered lists for steps, tables for comparisons, headings so a reader can find each part.
